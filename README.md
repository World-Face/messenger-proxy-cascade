# Messenger Proxy Cascade

Каскадный прокси **WhatsApp** и **Telegram MTProto**: клиенты подключаются к серверу в России, а наружу трафик выходит с зарубежного сервера. Между серверами — **Xray VLESS + REALITY**, снаружи неотличимый от обычного TLS 1.3.

```
Клиент ──► вход (РФ)                        выход (зарубеж) ──► g.whatsapp.net
           haproxy :8443 ─send-proxy─┐    ┌─► haproxy 127.0.0.1:8443
           haproxy :7777 ─send-proxy─┤    ├─► haproxy 127.0.0.1:7777 ──► whatsapp.net
           haproxy :9443 ────────────┤    ├─► mtg     127.0.0.1:9443 ──► Telegram DC
           haproxy :443  заглушка    ▼    │
                              xray dokodemo ──── VLESS + REALITY :443 ────► xray
```

## Зачем так

| | |
|---|---|
| **Домены смотрят на РФ** | Российские клиенты ходят на российский IP — быстро и без блокировок на «последней миле» |
| **Зарубежный выход** | WhatsApp и Telegram видят иностранный IP, к которому у них нет вопросов |
| **REALITY между серверами** | Транзит РФ→заграница выглядит как TLS-сессия к легитимному сайту. WireGuard/OpenVPN здесь ловятся ТСПУ по сигнатуре, REALITY — нет |
| **Реальный IP клиента** | PROXY-протокол проходит сквозь VLESS, поэтому Meta получает адрес клиента, а не адрес каскада |
| **Выход закрыт наружу** | Открыт единственный порт REALITY, и только для IP входного сервера. `haproxy` и `mtg` слушают `127.0.0.1` |
| **Заглушка на :443** | Сканер, постучавшийся в Telegram-порт с неверным секретом, получает валидный HTTPS обычного сайта вместо закрытого соединения |

## Установка

Установщик сам ставит зависимости, выпускает сертификаты, настраивает systemd и firewall. Спрашивает только то, что нельзя вычислить: **два домена на выходе и один токен на входе.**

Порядок важен: сначала выходной сервер — он выдаёт токен для входного.

### 1. Выходной сервер (зарубежный)

```bash
curl -sSL https://raw.githubusercontent.com/World-Face/messenger-proxy-cascade/main/install.sh -o /tmp/install.sh && sudo bash /tmp/install.sh exit
```

Спросит домен WhatsApp и домен Telegram. Свой публичный IP определит сам, IP входного сервера возьмёт из DNS этих доменов. В конце напечатает **токен** — длинную строку base64.

### 2. Входной сервер (российский)

```bash
curl -sSL https://raw.githubusercontent.com/World-Face/messenger-proxy-cascade/main/install.sh -o /tmp/install.sh && sudo bash /tmp/install.sh entry
```

Спросит только токен. Домены, порты, ключи REALITY и секрет Telegram приедут внутри него.

В конце входной установщик прогоняет сквозные проверки: запрашивает внешний IP через каскад и сверяет с адресом выходного сервера, затем дёргает заглушку по HTTPS. Обе зелёные — цепочка рабочая.

### Без интерактива

Любой вопрос можно ответить заранее переменной окружения — установщик спросит только недостающее:

```bash
WA_DOMAIN=whatsapp.example.com TG_DOMAIN=telegram.example.com AUTO_CONFIRM=y bash install.sh exit
```

```bash
TOKEN=<токен_с_выходного> AUTO_CONFIRM=y bash install.sh entry
```

Так же переопределяются `WA_CHAT_PORT`, `WA_MEDIA_PORT`, `TG_PORT`, `XRAY_PORT`, `SNI`, `EXIT_IP`, `ENTRY_IP`.

### Повторный запуск

Установщик идемпотентен. Ключи REALITY, UUID и секрет Telegram сохраняются в `/opt/messenger-proxy/state.env` и **переиспользуются** при повторном запуске — уже розданные клиентам ссылки продолжают работать.

Чтобы перевыпустить всю связку:

```bash
ROTATE=y bash install.sh exit
```

После этого обязательно переустановите входной сервер с новым токеном и раздайте клиентам новые ссылки — старые перестанут работать.

Секрет Telegram перевыпускается автоматически, если сменился домен: в него зашито доменное имя.

## Параметры

| Что | По умолчанию |
|---|---|
| Порт WhatsApp Chat | `8443` |
| Порт WhatsApp Media | `7777` |
| Порт Telegram | `9443` |
| Порт REALITY (вход→выход) | `443` |
| Маскировочный SNI | `vk.ru` |

DNS-записи обоих доменов должны указывать на **входной** сервер — установщик на это опирается.

## Подключение клиентов

**WhatsApp** — Настройки → Хранилище и данные → Прокси → адрес домена, порты Chat и Media.

**Telegram** — ссылка вида `https://t.me/proxy?server=...&port=...&secret=...` печатается в конце установки и лежит в `/opt/messenger-proxy/info.txt`.

## Заглушка и сертификаты

На входном сервере поднимается HTTPS-заглушка на `:443` с нейтральной страницей. Туда `mtg` отправляет соединения с неверным секретом, туда же попадают случайные сканеры — вместо `connection refused` они видят обычный небольшой сайт.

Сертификат берётся у Let's Encrypt автоматически:

1. **HTTP-01** через `:80` — предпочтительный путь, обновление без простоя.
2. **TLS-ALPN-01** через `:443`, если провайдер режет `:80`. Работает, но на время обновления (раз в ~60 дней) `haproxy` на несколько секунд освобождает порт. Откройте `:80`, чтобы этого избежать.
3. **Самоподписанный** — если оба способа недоступны. Заглушка останется, но камуфляж слабее.

Обновление и пересборку pem-файла берёт на себя `certbot` через `renewal-hooks`.

## Управление

```bash
systemctl status haproxy xray-cascade telegram-proxy
```

```bash
journalctl -u xray-cascade -f
```

Статистика HAProxy — на `127.0.0.1:8199`, смотреть через SSH-туннель:

```bash
ssh -L 8199:127.0.0.1:8199 root@ВАШ_СЕРВЕР
```

Сквозная проверка каскада с входного сервера (должен вернуться IP выходного):

```bash
curl -s --socks5-hostname 127.0.0.1:10808 https://api.ipify.org
```

Метрики mtg (Prometheus) — на выходном сервере, `http://127.0.0.1:3129/metrics`.

## Диагностика

**Telegram не подключается.** Посмотрите метрики `mtg` на выходном сервере:

```bash
curl -s http://127.0.0.1:3129/metrics | grep mtg_domain_fronting
```

Если `mtg_domain_fronting` растёт с каждой попыткой — `mtg` отвергает handshake и отправляет клиента в заглушку. Почти всегда это **устаревший секрет в клиенте**: сверьте ссылку с той, что выдаёт

```bash
mtg access /opt/messenger-proxy/telegram/config.toml
```

**Проверить, доходят ли клиенты до входного сервера** — счётчики фронтендов HAProxy:

```bash
echo "show stat" | socat stdio /run/haproxy/admin.sock | cut -d, -f1,2,5,8
```

**`mtg doctor` показывает ошибку SNI-DNS match** — так и должно быть:

```
Validate SNI-DNS match
  ❌ Hostname telegram.example.com is resolved to "<IP входа>", not <IP выхода>
```

Проверка рассчитана на односерверную установку и ждёт, что домен резолвится в IP выходного сервера. В каскаде домен обязан смотреть на входной.

## Требования

- Ubuntu 22.04 / 24.04, root. На 20.04 заглушка отключится (`haproxy` 2.0 не умеет `http-request return`), остальное работает
- Если у провайдера есть внешний firewall (security groups), откройте:
  - на **входном**: TCP `80`, `443`, `8443`, `7777`, `9443`
  - на **выходном**: TCP `443`

Нестандартные порты (`7777`, `9443`) режут некоторые провайдеры и мобильные операторы. Если клиенты не подключаются, а сервер их не видит — смените порты на привычные, например `2053` или `2083`.
